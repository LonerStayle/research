🔍 02 케이스 스터디 — "약한 모델 분리 17%" 는 왜 그렇게 낮았나

노트북 02_tool_consolidation_eval.ipynb 의 gpt-4.1-nano 분리안 17% 가 너무 낮아 보여, 원인을 추적하고 교란을 제거해 다시 측정한 기록. (원인 → 과정 → 결과)

TL;DR — 17% 는 과장이었다. 실패 12건 중 순수 도구설계 신호(threading)는 4건뿐, 나머지는 태스크 교란(구분자 4 + 전사/무답 2). 교란 제거 후 분리 17% → 39%, 통합 94% — 남은 실패는 거의 전부 threading.

구조(2도구·각1파라미터 vs 1도구·3파라미터)는 그대로, 교란만 제거:

3.5 왜 그래도 39% 인가 — 분리 실패의 실제 행동 (핵심)

교란을 다 없앴는데도 분리가 39% 밖에 안 되는 이유는 약한 모델이 한 도구의 출력을 다음 도구의 입력으로 이어붙이지(pipe) 못하기 때문이다. 클린 gpt-4.1-nano 분리 18건 실제 행동:

행동건수
정답7
normalize 부르고도 원본을 checksum10
기타(전사/algo)1

가장 흔한 실패(10건): normalize 를 호출은 하는데, 그 결과를 버리고 원본을 다시 checksum 에 넣는다.

  • K1: normalize('Hello World') → checksum_all('Hello World') → 답 1052(원본), 정답 1116. normalize 로 hello world 받아놓고 checksum 엔 원본 Hello World 를 다시 넣음.
  • K2: normalize('OrderHub Team') → checksum_all('OrderHub Team') → checksum_all('orderhub team') → 원본·정규화를 둘 다 계산해놓고 원본 결과(53659)를 최종답으로 보고(정답 10173) — 어느 중간결과가 최종답인지 못 고름.

즉 약한 모델은 ① 스텝은 알지만(normalize 부름) ② 출력을 다음 입력으로 파이프하지 못하고 원본을 다시 읽으며 ③ 때로 틀린 중간결과를 최종답으로 고른다. 반면 정규화 불필요한 raw 과제(K3·K5)는 거의 다 정답 → 실패는 체이닝이 필요한 과제에서만 난다. 이게 통합 compute() 가 도구 안에서 대신 해주는 composition 이라 — 통합 94% vs 분리 39%.

4. 결론

  • 측정 코드·검증기는 정상이었고(거짓통과/실패 0), 문제는 해시 태스크의 교란이 실패율을 부풀린 것.
  • 교란 제거 후에도 통합 > 분리 정확도 격차는 진짜(94% vs 39%), 원인은 약한 모델의 normalize→checksum threading 실패. 통합은 체이닝을 도구 안에서 없애 정확도를 지킴.
  • gpt-5-nano 는 교란 유무 무관 100%/100% — divergence 는 약한 모델 전용.
  • 교훈: 도구설계 A/B 는 최종답을 짧게·입력을 구분자 없이 둬야 도구 효과가 태스크 노이즈와 안 섞인다. 집계만 믿지 말고 실패를 원인별로 분해하라.
