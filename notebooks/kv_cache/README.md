# KV(프롬프트) 캐싱 비교 리서치

3사 4모델의 KV 캐싱 동작을 **동일한 실험 설계**로 측정하는 노트북 모음입니다.

> 📌 **모델별로 캐시 토큰을 어느 키에서 읽어야 하는지**만 필요하면
> → **[`CACHE_FIELD_REFERENCE.md`](CACHE_FIELD_REFERENCE.md)** (키 사용 표 · 추출 코드 · 과금 구조)

## 폴더 구성

| 폴더 | 모델 | 캐싱 방식 | 노트북 |
|---|---|---|---|
| `gpt56_luna/` | `gpt-5.6-luna` | 자동 프리픽스 | `gpt56_luna_kv_cache.ipynb` |
| `gpt54_mini/` | `gpt-5.4-mini` | 자동 프리픽스 | `gpt54_mini_kv_cache.ipynb` |

앞의 4개는 **단발 요청**(같은 프리픽스 반복)을, `multiturn_compare/` 는 **10턴 누적 대화**를 측정합니다.
각 노트북은 실행 후 같은 폴더에 `results.json`(멀티턴은 `multiturn_results.json`)을 남깁니다.

## 실행 방법

```bash
# 프로젝트 루트에서
uv run jupyter nbconvert --to notebook --execute --inplace \
  notebooks/kv_cache/gpt56_luna/gpt56_luna_kv_cache.ipynb
```

`.env` 에 필요한 키: `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GOOGLE_API_KEY`

**주의**
- 캐시 TTL 은 수 분입니다(GPT 5.6 만 최소 30분 보장). 셀을 띄엄띄엄 실행하면 evict 되므로 **한 번에 이어서 실행**하세요.
- **Gemini 무료 티어는 한도가 두 겹입니다** — 분당 5회(RPM)와 **하루 20회(RPD)**. 노트북의 스로틀링은 분당 한도만 해결하므로, 단발(10회) + 멀티턴(10회)을 같은 날 돌리면 **일일 한도에 걸려 잠깁니다**. 이때 나오는 `retryDelay: 5s` 는 오해를 부르는 값이라 재시도해도 풀리지 않습니다(PT 자정 리셋까지 대기). 노트북은 `quotaId` 에 `PerDay` 가 있으면 즉시 중단하고 안내하도록 해뒀습니다.
  - 429 가 계속 나면 에러의 `quotaId` 를 보세요. `...-FreeTier` 라면 결제를 연결한 프로젝트와 API 키의 프로젝트가 다른 것입니다.
- `gemini-3.6-flash` 와 opus 출력가는 **단가가 플레이스홀더**입니다. 절감률(%)은 유효하지만 절대 금액은 공식 pricing 으로 교체 후 보세요. (GPT 계열 단가는 공식 확인값으로 반영 완료)

## 실측 결과 요약 (20,000 토큰 · 반복 3회)

| 모델 | 캐시 적중률 | 비용 절감 | TTFT 개선 | 전체 latency 개선 |
|---|---|---|---|---|
| `gpt-5.6-luna` | **99.98%** | 88.7%* | +7.3% | −1.5% |
| `gpt-5.4-mini` | 98.99% | 88.1% | **+44.0%** | **+50.4%** |
| `claude-opus-4-8` | 99.86% | 89.4% | −7.7% | −8.3% |
| `gemini-3.6-flash` | 84.07% | 75.7% | +30.5% | +30.5% |

\* `gpt-5.6-luna` 의 비용 수치는 **캐시 쓰기 회계를 반영하기 전 구 단가 기준**입니다. 노트북은 수정됐으니 재실행하면 갱신됩니다(적중률·시간 수치는 그대로 유효).

### 이 표에서 읽어야 할 것

**1. 적중률과 시간 이득은 별개입니다.**
`gpt-5.6-luna` 는 적중률이 가장 높은데(99.98%) 시간 개선은 거의 없고, `gpt-5.4-mini` 는 적중률이 더 낮은데도 TTFT 가 44% 빨라졌습니다. 20K 규모에서는 prefill 자체가 수백 ms 라 네트워크·서버 부하 변동에 묻히기 때문입니다.
**→ 캐싱 작동 여부는 시간이 아니라 토큰 usage 필드로 판정하세요.** 시간 지표를 제대로 보려면 `TARGET_TOKENS` 를 100K~200K 로 올리거나 `N_REPEAT` 를 10 이상으로 늘리세요.

**2. 캐시 입자도가 세대별로 다릅니다.**
같은 프리픽스에서 `gpt-5.4-mini` 는 16,128 토큰(= 128 × 126)만 적중했습니다 — **128토큰 블록 단위**로 잡히고 나머지 꼬리는 매번 새로 계산됩니다. `gpt-5.6-luna` 는 16,289/16,292 로 거의 전량 적중해 **입자도가 더 세밀**합니다. 아래에서 보듯 이건 개선판이 아니라 **캐싱 메커니즘 세대가 다른 것**입니다.

**3. Gemini 암시적 캐싱은 조건이 까다롭습니다.**
이 노트북의 워밍업 적중률 추이는 `[0%, 84.1%, 0%, 0%]` 로 들쭉날쭉했지만, `litellm/` 폴더의 장기 실험에서 원인이 밝혀졌습니다 — **보장이 없어서가 아니라 ① 프리픽스가 ~10K 이상이어야 하고 ② 캐시가 ~8,125 토큰 블록 단위로만 늘며 ③ 호출 간격이 벌어지면 evict** 되기 때문입니다. 무료 티어 스로틀(13초 간격)이 ③에 걸렸던 것으로 보이며, 간격 없이 연속 호출하면 1회 워밍업 후 **14/15회 안정적으로 적중**합니다. 자세한 수치는 `litellm/README.md` 를 보세요.

## 멀티턴 비교 (`multiturn_compare/`) — 10턴 누적 대화

단발 벤치마크가 "같은 프리픽스를 반복하면 캐시가 걸리나"를 봤다면, 이쪽은 **턴이 쌓일 때 캐시가 계단식으로 따라 붙는가**를 봅니다. 실제 챗·에이전트의 동작에 더 가깝습니다.

동일하게 맞춘 것: 시스템 프롬프트(~2,000 토큰), 10턴 질문 시퀀스(턴마다 ~700 토큰 로그 발췌 첨부), 출력 한도, 지표.
API 구조상 맞출 수 없는 것: 각 API의 **권장 멀티턴 캐싱 방식**을 각자 적용했습니다.

| | OpenAI | Anthropic | Google |
|---|---|---|---|
| 멀티턴에서 개발자가 할 일 | `prompt_cache_key` 고정 (선택) | **매 턴 `cache_control` 을 마지막 user 블록으로 이동** (필수) | 없음 |
| 안 하면 | 그래도 자동으로 걸림 | **이전 대화가 캐시되지 않음** | — |

> **⚠️ 이 노트북은 아직 실행 전 상태입니다.** 직접 실행해서 결과를 채우세요.

### 예비 실행에서 확인된 것

첫 실행에서는 4모델 중 `gpt-5.4-mini` 만 완주했고(**턴2~10 평균 적중률 81.9%, 비용 절감 69.1%**), 나머지 3개는 아래 이유로 실패했습니다. **모두 수정 완료**된 상태입니다.

| 모델 | 실패 원인 | 조치 |
|---|---|---|
| `gpt-5.6-luna` | `temperature=0` **미지원** (기본 1만 허용) | `temperature` 를 3사 공통으로 미전송 |
| `claude-opus-4-8` | `temperature` 자체가 **deprecated** → 400 | 동일 |
| `gemini-3.6-flash` | 429 — 앞선 노트북 실행으로 **무료 쿼터 소진** | 재시도 강화 + 부분 결과 보존 |

수정 후 2턴 스모크 테스트로 검증했습니다 — `gpt-5.6-luna` 정상 실행, `claude-opus-4-8` 은 턴2에서 `cache_read` 2,023 토큰(73%)으로 **증분 캐싱 정상 작동**을 확인했습니다.

또한 어느 모델이 중간에 실패해도 **그 턴까지의 결과는 보존**되고 나머지 모델은 계속 돌도록 고쳤습니다.

**부수적으로 알게 된 것**: 최신 모델들은 `temperature` 를 아예 받지 않는 방향으로 가고 있습니다. 3사 공통 코드를 짤 때 샘플링 파라미터를 모델별로 분기하지 말고 **보내지 않는 쪽**이 안전합니다.

## 3사 캐싱 구조 비교

| | OpenAI 5.6+ | OpenAI 5.5 이하 | Anthropic | Google (암시적) |
|---|---|---|---|---|
| 켜는 방식 | 자동 (1024 토큰 이상) | 동일 | **명시적** `cache_control` | 자동 (끌 수 없음) |
| 개발자가 할 일 | `prompt_cache_key` (선택) | 동일 | 캐시 지점 직접 지정 (필수) | 없음 |
| **쓰기 비용** | **1.25배** | **없음** | **1.25배** (5분) / 2배 (1시간) | 없음 |
| 읽기 비용 | 입력가의 10% | 입력가의 ~10% | 입력가의 10% | 입력가의 ~10% |
| usage 필드 | `cached_tokens`<br>**`cache_write_tokens`** | `cached_tokens`<br>(write 는 항상 `None`) | `cache_creation_input_tokens`<br>`cache_read_input_tokens` | `cached_content_token_count`<br>(**미스 시 `None`**) |
| TTL 제어 | `prompt_cache_options.ttl="30m"`<br>(유일값, 최소 30분 보장) | `prompt_cache_retention`<br>(5~10분, 확장 24h) | 5분 (`ttl:"1h"` 옵션) | 수 분 |
| 히트 보장 | 프리픽스 일치 시 | 동일 | 프리픽스 일치 시 | **없음** |

**손익분기 (Anthropic·GPT 5.6 공통)**: 쓰기 1.25배를 읽기 90% 할인으로 회수하려면 같은 프리픽스를 **약 1.3회 이상** 재사용해야 합니다. 재사용이 없는 1회성 요청은 순손해입니다.

## GPT 5.6 세대 — 캐싱 회계가 바뀌었습니다

**5.6 부터 OpenAI 도 캐시 쓰기/읽기를 분리**해 리포트하고 **쓰기에 1.25배를 과금**합니다. Anthropic 의 2단 회계와 같은 구조가 OpenAI 에도 생긴 것입니다. 실측 usage 덤프:

```
gpt-5.6-luna  1회차(콜드): cache_write_tokens=6010, cached_tokens=0
              2회차(웜):   cache_write_tokens=0,    cached_tokens=6010
gpt-5.6-sol   동일
gpt-5.5       cache_write_tokens=None  (항상)
gpt-5.4-mini  cache_write_tokens=None  (항상)
```

**`gpt-5.6-luna` 공식 단가** (per 1M): input $1.00 · cached read $0.10 · **cache write $1.25** · output $6.00

> ⚠️ **실무 함의**: 5.6 부터는 **재사용 없는 1회성 요청이 오히려 1.25배 비쌉니다.** 5.5 이하에는 없던 리스크이므로, 단발 요청 위주 워크로드를 5.6 으로 올릴 때는 비용이 늘 수 있습니다. 멀티턴·에이전트처럼 재사용이 구조적으로 보장되는 워크로드는 거의 항상 이득입니다.

`gpt56_luna/` 노트북의 '쓰기/읽기 손익' 셀과 `multiturn_compare/` 의 '캐시 쓰기 리포트' 셀이 이 손익을 직접 계산합니다.

## Gemini 세대별 암시적 캐싱 — 정책은 같고, 안정성이 다릅니다

**문서상 정책에는 버전별 차이가 없습니다.** 암시적 캐싱은 2.5 이상 전 모델 기본 활성이고, 최소 토큰은 Flash 1024 / Pro 4096, 할인율도 동일합니다.

그런데 실측에서는 차이가 납니다 — 동일 프리픽스(14.3K 토큰) 연속 호출 시 적중률 추이:

```
gemini-3.6-flash        [0, 0, 57, 0, 0, 57, 57]   적중 3/7  ← 들쭉날쭉
gemini-3.5-flash        [57,57,57,57,57,57,57]     적중 7/7  ← 안정
gemini-3-flash-preview  [57,57,57,57,57,57]        적중 6/6  ← 안정
```

**적중률(57%)은 세대 공통인데 적중 안정성만 3.6 이 유독 낮습니다.** `gemini36/` 노트북 실행에서도 `[0%, 84%, 0%, 0%]` 로 같은 패턴이 나왔으니 일회성 노이즈는 아닙니다.

다만 이건 **정책 변경이라기보다 신모델의 인프라·캐시 풀 경합** 쪽으로 보는 게 타당합니다 — 문서에 3.6 전용 변경 기술이 없고 할인율·최소 토큰도 동일하기 때문입니다.

**추가 주의**: `tools` 를 정의하면 암시적 캐싱이 조용히 안 걸린다는 보고가 있습니다([vercel/ai#11513](https://github.com/vercel/ai/issues/11513), Gemini 3 Flash 대상). Google 공식 답변 없이 "not planned" 로 종료됐습니다. 에이전트에서 Gemini 캐싱을 기대한다면 확인이 필요한 지점입니다.

**Gemini 주의**: `cached_content_token_count` 는 미스일 때 `None` 으로 옵니다. 그냥 더하면 `TypeError` 가 나므로 항상 `or 0` 으로 방어하세요.
