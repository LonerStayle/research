## 세션 메모리 (Session Memory) — 이 대화 하나를 위한 노트

`src/services/SessionMemory/` 가 담당합니다. 파일 헤더 주석이 정의를 그대로 말해줍니다: *"현재 대화에 대한 노트 마크다운 파일을 자동 유지하며, 포크된 서브에이전트가 백그라운드에서 주기적으로 실행되어 메인 대화 흐름을 방해하지 않고 핵심 정보를 추출한다"* (`sessionMemory.ts:1-5`).

- **쓰는 주체가 메인 에이전트가 아닙니다.** 도구 호출 횟수가 임계값을 넘으면(`countToolCallsSince` → `hasMetUpdateThreshold`) 현재 대화를 통째로 복제한 포크 에이전트(`runForkedAgent`)가 백그라운드에서 돌아가 노트 파일을 Edit 도구로만 갱신하고 종료합니다. 메인 대화에는 이 과정이 전혀 보이지 않습니다.
- 형식이 **고정 10섹션 템플릿**입니다: Session Title / Current State / Task specification / Files and Functions / Workflow / Errors & Corrections / Codebase and System Documentation / Learnings / Key results / Worklog (`prompts.ts:11-41`). 섹션당 ~2,000, 전체 12,000토큰 캡.
- 존재 이유는 프롬프트에 명시돼 있습니다: *"Always update 'Current State' — this is critical for **continuity after compaction**"* (`prompts.ts:69`). 즉 컨텍스트가 꽉 차서 대화가 요약(컴팩션)으로 뭉개질 때, 이 노트가 유실 방지 백업 역할을 합니다. 그래서 `services/compact/sessionMemoryCompact.ts`(630줄)가 컴팩션과 직접 연동돼 있습니다.
- GrowthBook feature gate `tengu_session_memory` 뒤에 있어 **모든 사용자에게 켜져 있는 기능은 아닙니다** (`sessionMemory.ts:80-82`).

## 1. "MEMORY.md랑 summary.md랑 같이 있는 거구나" — 맞습니다, 층위만 다르게

## 2. 세션 메모리는 언제 발동하나

`registerPostSamplingHook`으로 등록된 훅이라 **모델 응답이 끝날 때마다** 검사되고, 실제 추출은 아래 조건을 전부 통과해야 합니다 (`src/services/SessionMemory/sessionMemory.ts:134-181, 272-289`):

**전제 조건** — ① 메인 REPL 스레드일 것(서브에이전트·팀메이트 제외), ② `tengu_session_memory` 게이트 ON, ③ 초기화 임계값: 대화 컨텍스트가 **10,000토큰** 이상 (`minimumMessageTokensToInit`, sessionMemoryUtils.ts:33)

**발동 조건** — 초기화 후에는 둘 중 하나:
```
(지난 추출 이후 컨텍스트 +5,000토큰 성장  AND  도구 호출 3회 이상)
또는
(+5,000토큰 성장  AND  마지막 어시스턴트 턴에 도구 호출 없음)  ← 자연스러운 대화 휴지점
```
토큰 성장 조건(`minimumTokensBetweenUpdate: 5000`)은 **항상 필수**입니다 — 도구를 아무리 많이 불러도 컨텍스트가 안 자랐으면 추출하지 않습니다 (주석에 "prevents excessive extractions"라고 명시, sessionMemory.ts:165-167). 조건이 맞으면 대화를 통째로 포크한 서브에이전트가 백그라운드에서 summary.md를 Edit하고 조용히 종료합니다.

## 3. "컴팩션 = /compact 할 때 그거?" — 절반만 맞습니다

`/compact`는 **수동 트리거**일 뿐이고, 같은 기계가 **자동으로도** 돕니다:

- **수동**: `/compact` 커맨드 (`src/commands/compact/`) → `compactConversation()` 직접 호출
- **자동 (autoCompact)**: 매 턴 컨텍스트가 임계값을 넘으면 사용자 개입 없이 발동. 임계값 = 모델 컨텍스트 윈도우 − 요약 출력 예약 20,000 − 버퍼 13,000토큰 (`src/services/compact/autoCompact.ts:30,62`). 200K 모델이면 대략 167K 부근에서 자동 발동합니다.
- 그 아래에 더 가벼운 단계들도 매 턴 돌고 있습니다 — 오래된 도구 결과만 지우는 microcompact 등, 5단계 전처리(applyToolResultBudget → snipCompact → microcompact → contextCollapse → autocompact)의 마지막 수단이 autocompact입니다 (분석 문서: `md_group/cc-context-preprocessing-timing.md`).

그래서 전체 그림을 이으면: **세션 메모리는 컨텍스트가 자라는 동안 5K토큰마다 백그라운드에서 노트를 갱신해 두고, 컨텍스트가 한계에 닿아 (자동이든 `/compact`든) 컴팩션이 터지는 순간 그 노트가 연속성 백업으로 쓰이는 구조**입니다.

## 2. LLM 인풋 타이밍 — 시스템 리마인더 아닙니다

세션 메모리는 **평소에는 LLM에 전혀 안 들어갑니다.** 매 턴 주입되는 게 아니라 디스크에서 잠자다가, **컴팩션이 터지는 그 순간 딱 한 번** 컨텍스트에 들어옵니다. 방금 읽은 주입 코드(`sessionMemoryCompact.ts:437-482`)를 보면 형태가 명확합니다:

```typescript
const summaryMessages = [
  createUserMessage({              // ← user 메시지!
    content: summaryContent,       //   summary.md 내용을 요약 틀에 담아서
    isCompactSummary: true,
    ...

## "엔터칠 때 같이 들어가?" — 자동 컴팩션이면 사실상 그렇습니다

autocompact 검사는 **엔터 친 후, API 호출 직전**의 5단계 전처리에서 돕니다. 그래서 그 엔터로 임계값을 넘긴 경우 순서는:

```

 → 내 질문이 배열에 append
 → 루프 시작: 전처리에서 임계값 초과 감지
 → 배열 재구성 (요약 메시지 삽입, 옛 메시지 제거)
 → API 호출  ← 요약과 내 질문이 "같은 요청"에 실려 나감
```

단, 항상 엔터 순간인 건 아닙니다 — 긴 턴 중간(도구 배치 사이)에 임계값을 넘으면 사용자 입력 없이도 터집니다.

## "별개의 인풋? 배열 최소 원소 2개?" — 맞고, 실제론 더 많습니다

요약은 내 질문에 합쳐지는 게 아니라 **독립된 user 메시지 원소**입니다. 컴팩션 직후의 API messages 배열은 대략:

```

  { role: 'user', content: '(보존된 최근 메시지들, 있다면)' },
  { role: 'user', content: '(SessionStart 훅 · 재주입된 파일 첨부)' },

```

user 메시지가 연달아 있어도 API는 허용합니다 (연속 동일 역할은 한 턴으로 합쳐 해석). 그러니 "최소 2개"는 맞고, 훅·첨부까지 치면 보통 그 이상입니다. `compact.ts:637-642`에서 결과 컨텍스트 크기를 셀 때도 정확히 이 조합(`boundaryMarker + summaryMessages + postCompactFileAttachments + hookMessages`)을 합산하죠.

```

## 1. 금지 목록의 공통점 — "이미 다른 정본이 있는 것"

저장 금지 항목을 다시 보면 패턴이 보입니다: 코드 패턴은 **grep이 정본**, git 히스토리는 **`git log`가 정본**(소스 원문: "authoritative"), 컨벤션은 **CLAUDE.md가 정본**, 디버깅 해법은 **코드와 커밋 메시지가 정본**. 전부 **매 세션 도구로 다시 파생 가능한(derivable) 정보**입니다.

이걸 메모리에 복사하면 정본이 둘이 됩니다. 코드는 바뀌는데 메모리는 안 바뀌니 반드시 낡고, 낡은 기억은 단순 무용이 아니라 **적극적으로 해롭습니다** — 그래서 소스에 `MEMORY_DRIFT_CAVEAT`과 "Before recommending from memory"(기억이 X가 있다고 말한다 ≠ X가 지금 있다) 같은 방어 섹션이 겹겹이 있는 거고요. **낡을 수밖에 없는 건 아예 안 적는 게 1차 방어, 검증 규칙은 2차 방어**인 구조입니다.

## 2. 4타입의 공통점 — "대화가 끝나면 영영 소실되는 것"

반대로 4타입을 보면: 사용자가 누구인지(user), 어떤 방식을 교정/확인했는지(feedback), 이 일을 **왜** 하는지 — 컴플라이언스 때문인지 기술부채 때문인지(project), 정보가 외부 어디에 있는지(reference). 이건 **코드를 아무리 grep해도 안 나옵니다.** 대화 속에만 존재하고, 세션이 끝나면 복구 불가능한 유일한 정보죠.

즉 자동 메모리는 "많이 기억하기"가 아니라 **"재파생 불가능한 정보만 골라 기억하기"**로 스코프가 잡혀 있습니다. 도구로 다시 얻을 수 있는 건 도구에게, 다시 얻을 수 없는 것만 메모리에게 — 저장소 간 분업입니다.

## 3. 노이즈의 해악이 실측돼 있음

"더 많이 기록하면 더 좋지 않나"에 대한 반증이 eval 기록에 있습니다:

- H2: "이번 주 PR 목록 저장해줘" 같은 요청을 그대로 저장하면 **활동로그 노이즈**가 됨 — 되묻기 게이트로 차단 (0/2 → 3/3)
- H5: 스냅샷성 기억으로 "최근 상태" 질문에 답하는 **오답 사례**가 실제 실패 모드로 계측됨

즉 메모리는 잘못 쓰면 0이 아니라 **마이너스**가 되는 기능이고, Anthropic은 그 마이너스를 측정해 본 상태에서 스코프를 좁힌 겁니다.

## 4. 경제성 — 좁아서 상시 탑승이 가능하다

MEMORY.md는 매 요청의 영구 승객입니다(200줄/25KB 캡). 코드 지식까지 쌓으면 인덱스가 즉시 비대해져서 캡에 걸리고, 컨텍스트를 오염시키고, 캐시 경제도 무너집니다. **스코프가 좁기 때문에 "항상 실린다"는 특권을 유지할 수 있는** 거죠.

## 5. 그런데 레버리지는 큽니다 — 실물 증거

이 프로젝트의 자동 메모리에는 딱 한 줄이 있습니다: *"레포 2-머신 공유 · 경로는 ~ 중립 표기"*. 정보량으로는 초라하지만, 이게 없으면 매 세션의 제가 문서에 절대경로를 박아서 **pull 충돌이 계속 재발**합니다. 실제로 한 번 겪고 저장된 기억이고요(git 로그의 "goldenplanet/seobi 머신 간 pull 충돌 방지" 커밋이 그 흔적).

- user 한 줄 = 모든 설명의 톤과 깊이가 조정됨
- project 한 줄 = "왜"를 알고 하는 제안과 모르고 하는 제안의 차이

## 1. 왜 "저걸" 기록하나 — 목적 문장과 4타입이 1:1로 맞물립니다

지침 ②의 목적 선언(`memdir.ts:241`)을 다시 보면:

| 협업의 질문 | 타입 | 이게 없을 때의 구체적 실패 |
|---|---|---|

| **HOW** — 어떻게 일하길 원하나 | `feedback` | 교정받은 실수를 다음 세션에 반복 — 사용자가 같은 걸 매번 다시 가르쳐야 함 |

즉 4타입은 임의의 카테고리가 아니라 **"세션 기억상실 에이전트가 겪는 실패 모드 목록"의 역상**입니다. 각 타입이 반복 발생하는 실패 하나씩을 정확히 겨냥합니다.

## 2. 왜 4개면 충분한가 — WHAT이 빠져 있기 때문입니다

협업에 필요한 지식을 축으로 나열하면 WHO / HOW / WHY / WHERE / **WHAT**(작업물 자체)인데, 파일 헤더 주석(`memoryTypes.ts:4-7`)이 마지막 축의 행방을 말해줍니다:

> "Memories are constrained to four types capturing context **NOT derivable from the current project state**. Code patterns, architecture, git history... are derivable (via grep/git/CLAUDE.md)"

**WHAT은 도구가 담당**합니다(grep/git/Read가 정본). 그걸 빼고 나면 남는 재파생 불가능한 축이 정확히 4개고, 그 4개를 전부 커버하니 "충분"한 겁니다. 임의로 4개를 고른 게 아니라 **5축 중 도구가 못 하는 것 전부**인 거죠.

## 3. 충분함의 실전적 근거 두 가지

**① 타입마다 "읽을 때의 사용법"이 다릅니다.** 분류는 서랍 정리용이 아니라 회상 시 행동 지침입니다 — user는 톤·깊이 캘리브레이션에, feedback은 행동 제약에, project는 의도 해석에(+ "빨리 낡으니 신선도 확인" 프로파일까지 타입에 내장), reference는 "가서 봐라" 트리거에. `<how_to_use>`가 타입마다 다르게 적혀 있는 이유입니다. **5번째 타입이 정당화되려면 5번째 사용 패턴이 있어야 하는데**, 위 4개로 안 덮이는 사용 패턴이 잘 없습니다.

**② 부족해졌을 때 Anthropic이 타입을 안 늘렸다는 증거.** 요구가 커졌을 때 실제로 한 일을 보면 — 팀 공유가 필요하자 타입 추가가 아니라 **스코프 축**을 추가했고(TEAMMEM: 같은 4타입에 private/team 스코프만 부여), 일상 기록이 필요하자 **별도 메커니즘**을 만들었고(KAIROS 데일리 로그), 세션 내 연속성이 필요하자 역시 별도 메커니즘(세션 메모리 10섹션)을 만들었습니다. **타입 축은 4개로 고정한 채 다른 축(스코프·수명)만 변주**하고 있다는 것 자체가, 이 분류가 안정적이라는 운영상의 방증입니다.

## 결정적 증거 — 라이브 버전엔 "red link"까지 있습니다

재미있는 발견인데, 미러 소스에는 없지만 **지금 이 세션의 제 시스템 프롬프트**(미러보다 최신 버전의 클로드코드)에는 이런 지침이 있습니다:

> "관련 메모리를 `[[name]]`으로 연결하라. **아직 존재하지 않는 메모리를 가리키는 `[[name]]`도 괜찮다 — 에러가 아니라 '나중에 쓸 가치가 있다'는 표시다.**"

이건 위키피디아의 **red link** 개념 그대로입니다 — 아직 안 쓰인 문서로의 링크가 "이 문서를 만들어라"는 신호가 되는 것. 방금 grep으로 확인했듯 미러 소스(`src/memdir/`)에는 `[[` 지침이 없으므로, **미러 스냅샷 이후 위키화가 한 단계 더 진행된 것**으로 보입니다. (이 프로젝트 관점에서 기록해 둘 만한 버전 차이입니다.)

## 왜 하필 위키 형태인가 — LLM에 맞게 번역하면

- **위키의 하이퍼링크 클릭 = LLM의 Read 도구 호출.** 목차만 상시 탑재(200줄 캡)하고 본문은 링크 따라 lazy loading — 위키의 탐색 모델이 그대로 컨텍스트 경제가 됩니다
- **description 프론트매터 = 검색 스니펫.** `findRelevantMemories`가 본문을 다 읽지 않고 description으로 관련성을 판단합니다
- **plain markdown = 사람도 편집 가능.** 사용자가 직접 파일을 열어 고칠 수 있는, 사람-LLM 공동 편집 위키인 셈이죠
