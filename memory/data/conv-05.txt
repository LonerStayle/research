[ASSISTANT] ## Codex 아키텍처 요약

**한 줄 요약**: Rust로 작성된 단일 엔진(`codex-core`)을 `app-server`라는 JSON-RPC 경계로 감싸고, TUI/exec/VSCode 확장/TS·Python SDK가 전부 그 경계를 통해서만 core와 통신하는 구조입니다.

### 레이어 구조
```
사용자/에디터/SDK
   ↓ (in-process 또는 JSON-RPC via stdio/ws/uds)
app-server ── Thread/Turn/Item API (유일한 공식 외부 경계)
   ↓
codex-core (비즈니스 로직 심장부)
   ├─ Session/Thread 상태 관리
   ├─ codex-api → LLM(OpenAI Responses API) SSE 스트리밍
   ├─ tools/ (ToolRouter) ── shell, apply_patch, MCP 도구, 서브에이전트 도구
   ├─ safety.rs + execpolicy → sandboxing (Seatbelt/Landlock/Windows)
   └─ ext/* 확장 (스킬, 메모리, 커넥터, goal, guardian 등)
   ↓
rollout(JSONL) + state(SQLite)로 영속화
```

# Codex 메인 루프 vs Claude Code: 8축 계산적 정교함 비교

## 1) 매 사이클 전처리 — 실제 순서

`run_turn` 루프 상단(`session/turn.rs:227~298`)의 실제 실행 순서:
1. `input_queue.get_pending_input`으로 대기 유저 입력 드레인(`turn.rs:231-235`) — 단, `can_drain_pending_input` 플래그가 false면 스킵(첫 스텝·auto-compact 직후엔 지연).
2. `run_hooks_and_record_inputs`로 드레인한 입력을 훅 통과 후 히스토리 기록(`turn.rs:237`).
3. `rollout_budget::maybe_record_reminder`(`turn.rs:242`).
4. `capture_step_context`로 `StepContext` 확보(`turn.rs:250-253`) — 이미 있으면(`next_step_context`) 재사용, 없으면 새로 캡처.
5. `time_reminder::maybe_record_current_time_reminder`(`turn.rs:255`).
6. `DeferredExecutor` 켜져 있으면 `record_step_world_state_if_changed`로 환경 상태 diff 주입(`turn.rs:262-270`).
7. `clone_history().for_prompt(...)`로 샘플링 입력 조립(`turn.rs:273-279`).
8. `run_sampling_request` 호출(`turn.rs:286`).

`run_pre_sampling_compact`는 루프 **밖**, 진입 직전 1회만(`turn.rs:158`). `context_window_token_status` / `token_budget::maybe_record` / `should_roll_over→run_auto_compact`는 전처리가 아니라 **샘플링 후처리**(`turn.rs:314-382`)에 있습니다 — 즉 Codex는 "실행 후 토큰 상태를 재고 다음 사이클로 넘어가기 전 압축"하는 구조. Claude Code가 사이클 진입 전 압축을 재는 것과 위치가 반대이지만 기계적 정교함은 동등합니다.

## 2) 위드홀드(withhold) 패턴 — 같다

Codex는 스트리밍 중 도구를 **즉시 실행하지 않습니다**. `OutputItemDone`에서 도구 호출을 만나면 `handle_output_item_done`이 실행 퓨처를 만들어 `in_flight: FuturesOrdered`에 push만 합니다(`turn.rs:2143-2144`, `stream_events_utils.rs:350-357`). 실제 대기/실행은 스트림 루프가 `Completed`로 끝난 **후** `drain_in_flight`에서 일어납니다(`turn.rs:2493`, 정의 `turn.rs:1907`). 결과는 거기서 `record_conversation_items`로 히스토리에 기록됩니다(`turn.rs:1915-1917`).

단, 미묘한 차이: 도구 호출을 나타내는 `ResponseItem` **자체**(호출 기록)는 스트리밍 도중 `record_completed_response_item`으로 즉시 기록되고(`stream_events_utils.rs:346`), 도구 **출력**만 위드홀드됐다가 drain 시 기록됩니다. Claude Code의 "withhold-then-batch"(도구 호출을 모아뒀다가 배치 실행)와 본질적으로 동일한 패턴입니다. `FuturesOrdered`라 방출 순서도 호출 순서로 보존됩니다.

## 3) 도구 스마트 배치/병렬 — RwLock 게이트

`ToolCallRuntime::handle_tool_call_with_source`(`tools/parallel.rs:94`)가 각 도구를 `tokio::spawn`으로 띄우되, 공유 `parallel_execution: Arc&lt;RwLock&lt;()&gt;&gt;` 게이트를 통과시킵니다(`parallel.rs:133-137`): 병렬 지원 도구는 `lock.read()`(동시 실행 허용), 비병렬 도구는 `lock.write()`(배타적 직렬화). 병렬 가능 여부는 `router.tool_supports_parallel(&amp;call)`(`router.rs:99`)로 레지스트리가 도구별로 선언합니다.

Claude Code의 `partitionToolCalls`(읽기전용 도구를 배치로 묶어 병렬)와 목표는 같지만 **메커니즘이 다릅니다**: Claude Code는 사전에 정적 분할해서 배치를 만들고, Codex는 개별 퓨처가 런타임에 read/write 락을 잡아 동적으로 조정합니다. Codex 방식이 오히려 더 세밀(도구가 섞여 들어와도 read 도구끼리는 동시에, write 도구가 오면 그 지점만 배타). 정교함은 동등 이상.

## 4) 도구 실행 파이프라인 단계 — ToolOrchestrator::run

`orchestrator.rs:137`의 `run`이 도구 하나에 대해 거치는 단계(주석에 "approval → sandbox 선택 → attempt → escalated retry"로 명시, `orchestrator.rs:4-6`):
1. workspace_roots → permission profile 물질화 → `to_runtime_permissions()`로 파일/네트워크 샌드박스 정책 계산(`orchestrator.rs:155-165`).
2. `exec_approval_requirement` 계산(도구 제공 or 기본값)(`orchestrator.rs:166-168`).
3. **승인 분기**: `Skip`(자동승인 or strict 시 guardian) / `Forbidden`(거부) / `NeedsApproval`(유저 결정 대기)(`orchestrator.rs:169-226`).
4. `sandbox_override_for_first_attempt` + `should_sandbox` 결정(`orchestrator.rs:228-244`).
5. `select_initial`로 `SandboxType` 선택(`orchestrator.rs:245-255`).
6. `SandboxAttempt` 조립(`orchestrator.rs:264-282`).
7. `run_attempt` 1차 실행(`orchestrator.rs:285-292`).
8. 성공→반환 / `SandboxErr::Denied`→에스컬레이션 분기(`orchestrator.rs:294-305`).
9. 네트워크 승인 컨텍스트 추출 + 정책 bail 검사(`escalate_on_failure`, `unsandboxed_allowed` 등)(`orchestrator.rs:306-390`).
10. 재시도 승인(strict면 fresh guardian review, 아니면 bypass 판정)(`orchestrator.rs:394-421`).
11. 재시도 샌드박스 재계산(`orchestrator.rs:423-445`).
12. `retry_attempt` 조립 + `run_attempt` 2차 실행(`orchestrator.rs:446-469`).

**12단계**로, Claude Code의 ~10단계보다 **오히려 많습니다**. 특히 "거부 시 재승인 후 에스컬레이션 재실행"은 Codex 고유의 추가 정교함입니다.

## 5) tool_results 묶음 + 리마인더 주입

Codex는 도구 출력 자체에 어태치먼트를 인라인으로 붙이진 않지만, **turn 루프 레벨에서 컨텍스트성 `ResponseItem`을 히스토리에 삽입**합니다. 샘플링 후처리에서 `token_budget::maybe_record`(`session/token_budget.rs:6`)가 (a) 남은 토큰이 임계 이하면 `TokenBudgetReminder`를, (b) 0이면 `AutoCompactFallbackPrompt`를 `record_conversation_items`로 주입합니다(`token_budget.rs:32-60`). 전처리에서는 `time_reminder`(`turn.rs:255`), `DeferredExecutor` 시 world_state diff(`turn.rs:262-270`, `record_step_world_state_if_changed`가 환경 변화를 `ContextualUserFragment`로 주입, `mod.rs:2821-2826`)가 들어갑니다. 모두 `ContextualUserFragment::into`로 만든 별도 유저 fragment 항목입니다. Claude Code의 system-reminder 주입과 기능적으로 대응하되, Codex는 이를 tool 출력에 붙이지 않고 히스토리 스트림에 독립 항목으로 끼워넣습니다.

## 6) 다음 사이클 컨텍스트 전처리

재호출 직전 `clone_history().await.for_prompt(&amp;model_info.input_modalities)`(`turn.rs:273-279`, `run_sampling_request` 재시도 루프에서도 `turn.rs:1164-1167`). `for_prompt`(`context_manager/history.rs:141`)는 `normalize_history` + 모달리티에 이미지 없으면 이미지 스트립을 수행합니다. 절단(`TruncationPolicy`)은 이 시점이 아니라 항목이 히스토리에 **들어올 때** `record_items`(`history.rs:121-135`)에서 이미 적용됩니다 — 즉 Codex는 "기록 시 절단, 방출 시 정규화"로 2단 분리. Claude Code가 매 사이클 재조립 시 정규화하는 것과 동등하되 절단 타이밍이 앞당겨져 있습니다.

## 7) prompt caching (KV) — **가장 큰 차이**

**Codex는 클라이언트에서 cache breakpoint를 심지 않습니다.** 전 코드베이스에 `cache_control`/`CacheControl`/`addCacheBreakpoint`가 프롬프트 캐싱 용도로 **전무**(grep 결과 `ephemeral`은 remote-control 전송 계층 무관 코드뿐). 대신 Responses API 요청에 `prompt_cache_key: Some(...)` 한 필드만 실습니다(`client.rs:888`, `903`). 키 값은 `prompt_cache_key()`(`client.rs:469-473`)로 = override 있으면 그것, 없으면 `responses_metadata.session_id` — 즉 **세션 단위 안정 키**. 이는 OpenAI Responses API의 **서버측 자동 prefix 캐싱**을 트리거하는 힌트일 뿐, 클라이언트가 어느 지점을 캐시할지 breakpoint를 지정하지 않습니다.

Claude Code(`addCacheBreakpoints`로 system/tools/history 경계에 `cache_control: ephemeral`을 명시 삽입)와 **근본적으로 다릅니다**: Claude(Anthropic API)는 캐시 경계를 클라이언트가 능동 제어, Codex(OpenAI Responses API)는 안정 키만 주고 캐싱 전략을 서버에 위임. 이 축에서 Codex 루프는 Claude Code보다 **덜 계산적**입니다(구조적으로 API가 그걸 요구하지 않기 때문이지, 게으른 게 아님).

## 8) 이어서 할지 판단 — 순수 needs_follow_up

계속 여부는 **reasoning/thinking으로 판단하지 않습니다**. 순전히 `needs_follow_up = model_needs_follow_up || has_pending_input`(`turn.rs:328`)로 결정. `model_needs_follow_up`이 true가 되는 경우: (a) 도구 호출이 큐잉됨(`output.needs_follow_up=true`, `stream_events_utils.rs:356`), (b) `Completed { end_turn: Some(false) }`(`turn.rs:2321-2323`), (c) RespondToModel 직접응답. `end_turn`은 모델이 명시적으로 턴 종료를 선언했는지의 신호이며 `Some(false)`면 강제 재호출, `None`이면 도구 유무로 폴백(`codex-api/common.rs:93-95` 주석). `reasoning_effort`/`reasoning_summary`는 요청 파라미터와 트레이싱에만 쓰이고(`turn.rs:1989-1990, 2009, 2024`) 루프 제어에는 **전혀 관여하지 않습니다**. Claude Code가 stop_reason으로 판단하는 것과 동일한 결정론적(비-추론) 방식.

# 사용자의 8단계 모델 — 실제 코드 검증

핵심 전제: 이 8단계는 `queryLoop`의 `while(true)`(`src/query.ts:305`) 한 바퀴에 해당합니다. **[확정]**

## 1) 전처리 — 정확함, 순서 보강

**[확정]** 매 반복 시작 시 실제 순서(`query.ts`):
① `getMessagesAfterCompactBoundary`(362) 마지막 compact 경계 이후만 슬라이스 → ② `applyToolResultBudget`(376) 도구결과별 크기 예산(초과분 디스크 이관) → ③ `snipCompactIfNeeded`(400, HISTORY_SNIP 게이트) → ④ `deps.microcompact`(411) 오래된 tool_result를 요약 없이 캐시편집으로 제거 → ⑤ `contextCollapse`(436, 게이트) → ⑥ `appendSystemContext`로 `fullSystemPrompt` 조립(444) → ⑦ `deps.autocompact`(449, `autoCompactIfNeeded`) 임계값 초과 시 LLM 요약 압축 → ⑧ 하드 차단 검사(632, `isAtBlockingLimit`). microcompact가 autocompact보다 먼저(주석 409)라는 점이 핵심.

## 2) "위드홀드 패턴" — ★부분적으로 틀림★

**[확정]** 사용자 이해("도구 선시작 + 결과를 보류했다가 배치로 방출")는 **절반만 맞습니다.**
- **선시작은 맞음**: 스트림 도중 `tool_use` 블록이 도착하면 `streamingToolExecutor.addTool`(`query.ts:833`)이 즉시 `processQueue → executeTool`로 실행을 시작합니다.
- **"보류 후 배치 방출"은 틀림**: `getCompletedResults`(`StreamingToolExecutor.ts:412`)는 완료된 도구 결과를 **완료 즉시, 스트림 도중에** yield합니다(`query.ts:842-852`). 붙들어뒀다 한꺼번에 내보내지 않습니다. 유일한 제약은 **순서**입니다 — 비동시성(쓰기) 도구가 배리어가 되어 그 뒤 결과는 대기(`StreamingToolExecutor.ts:436-438` `break`). 즉 "hold-and-batch-release"가 아니라 "eager-emit-in-order"입니다.
- **코드에 실재하는 'withhold'는 다른 것**: `query.ts:790-816`의 `withheld` 변수는 **도구 결과가 아니라 에러 메시지**(prompt-too-long/max-output-tokens/media-size)를 복구 루프가 회복 가능 여부를 판단할 때까지 SDK 호출자에게 방출 보류하는 장치입니다(`isWithheldPromptTooLong`/`isWithheldMaxOutputTokens`, `query.ts:790-813`). 사용자가 이 둘을 혼동한 것으로 보입니다.

## 3) 스마트 배치 — 정확함

**[확정]** `partitionToolCalls`(`toolOrchestration.ts:91`)는 `reduce`로 순회하며 각 도구의 `isConcurrencySafe`(`toolOrchestration.ts:98-108`, zod 파싱 성공 + `tool.isConcurrencySafe(input)` true)를 판정합니다. **연속된 안전 도구는 직전 배치가 안전 배치일 때만 같은 배치에 push**(`:109-110`), 아니면 새 배치를 엽니다(`:111-112`). 결과적으로 배치는 "단일 쓰기 도구" 또는 "연속 읽기전용 묶음" 둘 중 하나(주석 `:86-90`). 안전 배치는 `runToolsConcurrently`(`:152`)에서 `all(tasks, getMaxToolUseConcurrency())`로 병렬(기본 10, `:8-12`), 비안전은 `runToolsSerially`(`:118`)로 직렬. 쓰기 도구 하나가 배치를 끊는다는 이해가 정확합니다.

## 4) 도구 "10단계 파이프라인" — 정확함 (실제 ~10단계)

**[확정]** `runToolUse`(`toolExecution.ts:337`) → `checkPermissionsAndCallTool`(`:599`) 내부를 세면 실제로 10단계입니다:
1. **zod 스키마 검증** `inputSchema.safeParse`(`:615`) — 실패 시 InputValidationError tool_result

5. **권한 결정** `resolveHookPermissionDecision → canUseTool`(`:921-930`)

## 7) 과다 전송 + KV 캐싱 — 정확함, 배치 전략 확정

## 반전 포인트 2개

**① 사용자님이 CC에 대해 상상한 "보류 후 배치 방출"은 사실 CC가 아니라 Codex가 합니다.**
- CC의 `StreamingToolExecutor`는 도구가 끝나는 즉시(스트림 도중) 순서만 지켜 **바로 방출**합니다(eager-emit). 붙들어두지 않아요.
- 오히려 **Codex**가 스트리밍 중엔 도구 호출을 `in_flight` 큐에 **모으기만** 하고, 스트림이 `Completed`로 끝난 **뒤** `drain_in_flight`에서 한꺼번에 실행·기록합니다. 진짜 "hold-then-batch"는 Codex 쪽입니다.

**② 도구 실행 파이프라인은 Codex가 더 깁니다** — CC 10단계 vs Codex 12단계. Codex는 "거부 → 재승인 → 언샌드박스 에스컬레이션 재실행"이라는 추가 정교함이 있어요(커널 샌드박스를 쓰기 때문).

## 사용자님 이해 교정 2건 (CC 기준)

- **"withhold 패턴 = 도구 결과 보류 후 배치"** → 절반만 맞음. 선(先)시작은 맞지만 결과는 **완료 즉시 순서대로 방출**. 코드에 실제 있는 `withheld` 변수는 도구 결과가 아니라 **에러 복구용**(prompt-too-long, max-output-tokens 등을 회복 가능할 때까지 방출 보류)입니다.
- **"이어서 할지 thinking에서 판단"** → **틀림.** thinking은 루프 제어에 전혀 관여 안 합니다. `tool_use` 블록 존재 여부(`needsFollowUp`) **하나로만** 결정하고, `stop_reason`조차 안 믿습니다(코드 주석에 명시). Codex도 똑같이 `needs_follow_up`만 봅니다.

## 한 줄 요약

**"계산적 정교함"의 총량은 대등하되, 무게중심이 다릅니다.** Claude Code는 **컨텍스트·캐싱 레이어**(어태치먼트 종류 + `cache_control` breakpoint를 클라이언트가 직접 심는 3전선 전략)에 정교함이 실려 있고, Codex는 **도구 실행·안전 레이어**(12단계 승인-샌드박스-에스컬레이션 + 동적 병렬 게이트)에 실려 있습니다. # Codex 도구 실행에 박힌 기능적 규칙/휴리스틱 (codex-rs 검증)

## 1) 파일 편집 전 검증 — "Read→Edit"의 Codex 대응 [HARD] · **다름(같은 보장, 다른 메커니즘)**

**(a) 무엇을 하나:** Codex의 `apply_patch`는 편집 전 파일을 **매번 새로 읽고**(`apply-patch/src/lib.rs:606`, `:681` `fs.read_file_text(path)`), 패치의 context 라인(`change_context`)과 `old_lines`가 **현재 파일 내용과 실제로 일치하는지** `seek_sequence`로 검증한 뒤에만 적용합니다. `seek_sequence`(`apply-patch/src/seek_sequence.rs:12`)는 **4단계 점감 엄격도**로 매칭합니다: (1) 정확 일치 → (2) 후행 공백 무시(rstrip) → (3) 양쪽 trim → (4) 유니코드 문장부호 정규화(`seek_sequence.rs:76-107`, 하이픈/따옴표/비단절공백을 ASCII로 치환하는 `git apply` 유사 퍼지 매칭). 매칭 실패 시 `compute_replacements`가 `"Failed to find context '{ctx}'"`(`lib.rs:736`) 또는 `"Failed to find expected lines"`(`lib.rs:791`) 에러로 **적용을 거부**합니다.

**(b) 하드/소프트:** 코드 강제(HARD). 모델이 파일 현재 상태를 모르면 패치가 매칭되지 않아 물리적으로 편집 불가.

**(c) Claude Code 대비:** Claude Code는 **별도 상태 추적**(파일을 Read했는지 플래그로 기억, 안 읽었으면 Edit 거부, mtime 변하면 재-Read 요구)을 씁니다. Codex에는 그런 freshness/mtime/last_read 추적이 **전혀 없습니다**(grep 확인: `mtime`/`stale`/`last_read`/`has_been_read` 무매칭). 대신 **content 매칭 자체**가 그 역할을 합니다 — "먼저 Read해야 한다"는 상태 게이트 대신 "패치 context가 실제 내용과 맞아야 한다"는 내용 검증으로 대체. 결과 보장은 유사(틀린 가정으로 편집 못 함)하지만 메커니즘은 근본적으로 다릅니다.

## 2) execpolicy — Starlark 명령 정책 [HARD] · **있음(더 강력)**

**(a):** 셸 명령은 Starlark 기반 정책(`default.rules`, `core/src/exec_policy.rs:52`)으로 판정됩니다. 판정 결과는 `Decision::{Allow, Prompt, Forbidden}`(`execpolicy/src/decision.rs:9-15`). 규칙 종류는 `PrefixRule`(고정 토큰 or 대안 토큰 집합인 `PatternToken`으로 명령 prefix 매칭, `execpolicy/src/rule.rs:16-111`), `HeuristicsRule`, `NetworkRule`(프로토콜/호스트 규칙, `rule.rs:118-149`). 흐름: `create_exec_approval_requirement_for_command`(`exec_policy.rs:280`)이 명령을 정책에 넣어(`resolve_host_executables: true`로 실제 실행파일 해소, `exec_policy.rs:306`) `Decision`을 얻고, 이를 `ExecApprovalRequirement::{Skip, NeedsApproval, Forbidden}`으로 매핑(`exec_policy.rs:329-390`).

**(b):** HARD.

**(c) Claude Code 대비:** Claude Code도 allow/deny/ask 권한 규칙이 있지만 **정적 패턴**입니다. Codex는 **프로그래밍 가능한 Starlark DSL**로 더 표현력이 높습니다(호스트 실행파일 해소, prefix 대안 토큰 등). 유사 기능 있음, Codex가 더 정교.

## 3) 승인 캐싱/재사용 [HARD] · **있음(세션 + 영속 둘 다)**

**(a):** 두 층위의 캐싱이 있습니다. **세션 캐시:** `with_cached_approval`(`tools/sandboxing.rs:71`)이 세션 스코프 `tool_approvals` 스토어를 키(명령/파일 경로)별로 관리 — 모든 키가 `ApprovedForSession`이면 프롬프트를 건너뛰고(`sandboxing.rs:88-96`), 사용자가 "이 세션 동안 허용"을 고르면 키별로 저장(`sandboxing.rs:109-114`). apply_patch가 여러 파일을 건드리면 각 파일 키를 개별 저장해 부분집합 재요청도 스킵. **영속 캐시:** 사용자가 승인하면 execpolicy에 allow prefix 규칙을 **디스크(`default.rules`)에 영구 추가**할 수 있고(`exec_policy.rs:409-440` `add_prefix_rule(..., Decision::Allow)`, `session/mod.rs:1982` `persist_execpolicy_amendment`), 이를 알리는 `ApprovedCommandPrefixSaved` 컨텍스트 fragment를 히스토리에 주입(`mod.rs:2032`). MCP 도구 승인도 `remember_mcp_tool_approval`로 세션 기억(`mcp_tool_call.rs:1940-2005`).

**(b):** HARD.

**(c) Claude Code 대비:** Claude Code의 세션 내 "always allow" 기억과 대응(있음). 추가로 Codex는 **세션을 넘어 파일로 영속되는 prefix 규칙 amendment**까지 있어 더 강함.

## 4) 도구 순서/스킵/dedup — **없음(확정)**

**(a):** 대화 내용을 보고 도구 실행을 건너뛰거나 중복 호출을 감지·제거하는 로직은 **없습니다**. grep 결과 `dedup`/`duplicate` 매칭은 전부 무관(PATH 중복 제거 `runtimes/mod.rs:332`, CSV 헤더 검증, 테스트 이름). 모델이 요청한 도구 호출은 그대로 전부 실행됩니다. Codex의 "스마트함"은 실행 스킵이 아니라 병렬화(축 5)에 있습니다.

**(c) Claude Code 대비:** Claude Code에도 대화 기반 도구 스킵/dedup은 사실상 없음 — 양쪽 동일. **없음으로 확정.**

## 5) 병렬 안전성 판정 [HARD] · **있음(다름)**

**(a):** `ToolExecutor` 트레잇 기본값은 `supports_parallel_tool_calls = false`(`tools/src/tool_executor.rs:64-66`) — **보수적으로 기본 직렬화**. 도구가 명시적으로 opt-in: shell=`true`(`handlers/shell/shell_command.rs:152`), unified exec=`true`(`exec_command.rs:96`), view_image/tool_search=`true`. **MCP 도구는 스마트 판정**: 자체 `supports_parallel_tool_calls` 플래그 또는 서버가 광고한 `read_only_hint` 어노테이션이 true면 병렬 허용(`handlers/mcp.rs:76-86`). 라우터가 `tool_supports_parallel`(`router.rs:99`)→`registry.supports_parallel_tool_calls`(`registry.rs:385`)로 조회하고 Hidden 도구는 강제 비병렬(`registry.rs:271`). 최종 실행은 `parallel.rs:133`의 RwLock read(병렬)/write(직렬) 게이트.

**(b):** HARD.

**(c) Claude Code 대비:** Claude Code는 읽기전용 도구를 정적으로 partition해 배치 병렬. Codex는 **도구별 선언 플래그 + MCP read_only_hint + 런타임 RwLock**. 목표 동일, 메커니즘 다름. MCP의 read_only_hint 존중은 Codex 고유의 세밀함.

## 6) 샌드박스 에스컬레이션 지능 [HARD] · **Codex 고유(Claude엔 없음)**

**(a):** 1차 실행이 `SandboxErr::Denied`로 거부되면 지능적 재시도 판정: `escalate_on_failure()`(`orchestrator.rs:326`), `unsandboxed_execution_allowed(정책)`(`orchestrator.rs:339`), `wants_no_sandbox_approval(approval_policy)`(`orchestrator.rs:344`)를 순차 검사. `Never`/`OnRequest` 정책에선 언샌드박스 재시도를 **하지 않고** 원본 출력을 보존한 간결한 거부를 반환(`orchestrator.rs:341-380`). 재시도가 허용되면 (bypass가 아닌 한) **새 승인**을 받고(`orchestrator.rs:394-421`) 에스컬레이션된 샌드박스/언샌드박스로 2차 실행(`orchestrator.rs:446-469`). 네트워크 거부는 별도 `network_approval_context`로 호스트 단위 승인 유도.

**(b):** HARD.

**(c) Claude Code 대비:** Claude Code엔 OS 레벨 샌드박스 거부→에스컬레이션 재승인 재시도 개념이 없음. **Codex 고유 지능.**

# 도구 실행에 박힌 지능적 규칙 — 기능별 (하드/소프트)

태그: **[하드]** = 코드가 강제/거부, **[소프트]** = 시스템 프롬프트로 유도만.

## 1) Read→Edit 강제 — ★실재함★ [하드] + [소프트] 이중

**[확정][하드]** 실제로 코드로 강제됩니다. `FileEditTool.validateInput`(`FileEditTool.ts:275-287`)이 `toolUseContext.readFileState.get(fullFilePath)`를 조회해, 항목이 없거나 부분뷰(`isPartialView`)면 `{result:false, message:'File has not been read yet. Read it first before writing to it.', errorCode:6}`를 반환합니다. 동일 규칙이 `FileWriteTool.ts:198-203`, `NotebookEditTool.ts:221-226`에 있습니다.

강제 지점: `validateInput`이 `result:false`를 주면 `checkPermissionsAndCallTool`(`toolExecution.ts:683-687`)이 **`tool.call` 실행 전에** 에러 tool_result를 반환하고 종료합니다(파이프라인 2단계). 즉 도구가 아예 실행되지 않습니다.

`readFileState`는 `FileReadTool.call`이 채웁니다(`FileReadTool.ts:842-844`, `timestamp: Math.floor(stats.mtimeMs)` + content 저장). Edit/Write 성공 후에도 갱신(`FileEditTool.ts:520`, `FileWriteTool.ts:332`).

**[소프트]** 프롬프트에도 명시: "You must use your Read tool at least once in the conversation before editing. This tool will error if you attempt an edit without reading the file."(`FileEditTool/prompt.ts:5`). 소프트 유도와 하드 강제가 함께 걸린 이중 안전장치입니다.

## 2) 파일 freshness/staleness — ★실재함★ [하드 거부] + [자동 리마인더]

**[확정][하드]** 읽은 뒤 파일이 외부에서 바뀌면 편집을 거부합니다. `FileEditTool.ts:290-311`: `getFileModificationTime(fullFilePath) &gt; readTimestamp.timestamp`이면 `{result:false, message:'File has been modified since read, either by the user or by a linter. Read it again before attempting to write it.', errorCode:7}`. Windows 오탐 방지를 위해 풀리드일 때 content 동일성 fallback 비교(`:296-300`).

**[확정][자동 리마인더]** 별도로 매 턴 `getChangedFiles`(`attachments.ts:2063`)가 `readFileState`의 모든 파일을 순회하며 `mtime &gt; fileState.timestamp`인 파일을 재읽기해 변경 구간 diff를 `edited_text_file` 첨부로 삽입합니다(`attachments.ts:2115-2122`). 호출 지점은 `getAttachmentMessages` 내부 `maybe('changed_files', ...)`(`attachments.ts:871`) — 즉 루프의 도구 실행 후 첨부 단계(`query.ts:1569`)에서 모델에게 "이 파일이 바뀌었다"를 자동 통지합니다.

## 3) 툴 콜링 순서 규칙 — 대부분 [소프트], 하나만 [하드]

**[확정]** 시스템 프롬프트의 소프트 규칙:
- 전용 도구 우선, Bash 지양: `prompts.ts:301-305` ("Do NOT use Bash when a relevant dedicated tool is provided... CRITICAL"). **[소프트]** — 코드 강제 아님.
- 병렬 호출 권장: `prompts.ts:310` ("call multiple tools in parallel... Maximize parallel"). **[소프트]** (단, `partitionToolCalls`가 읽기전용을 물리적으로 병렬화하므로 실행층에서 부분 실현).
- 도구 호출 전 콜론 금지: `prompts.ts:438,770`. **[소프트]**.
- Edit 전 Read: `FileEditTool/prompt.ts:5`. **[소프트]이자 유일하게 [하드]** (위 1번).

정리: 순서 규칙 중 **코드로 강제되는 것은 Read→Edit뿐**이고, "전용도구 우선/병렬/콜론"은 전부 프롬프트 유도입니다.

## 4) 도구 실행 스킵/단축/dedup — ★코드에 없음★ [소프트만]

**[확정]** "대화를 보고 이미 아는 정보면 도구 실행을 건너뛰거나, 중복 호출을 감지해 캐시 결과를 재사용하는" **실행 스킵/dedup 로직은 오케스트레이션·실행기 어디에도 없습니다.** `toolOrchestration.ts` / `StreamingToolExecutor.ts` / `toolExecution.ts` grep 결과, "duplicate"는 형제 에러 중복 방지(`StreamingToolExecutor.ts:328`), "skip"은 결과 remap 생략(`toolExecution.ts:1291`)일 뿐, 실행 자체를 건너뛰는 판정은 없습니다. 모델이 요청한 tool_use는 권한만 통과하면 **항상 실행**됩니다.

유일하게 존재하는 "재사용"은 실행 스킵이 아니라 **KV 프롬프트 캐싱**(cache_control ephemeral, `claude.ts:3063`)과 tool_result 디스크 저장(`applyToolResultBudget`)입니다 — 둘 다 토큰/전송 최적화이지 실행 생략이 아닙니다. 따라서 "대화 보고 도구 건너뛰는 스마트함"은 **코드 기능이 아니라 순전히 모델이 프롬프트 유도로 스스로 판단**하는 소프트 영역입니다.

## 5) 스마트 입력 처리 — [하드] 자동 보정

**[확정]** 세 계층:

## 6) 권한 자동 결정 — [하드] 우선순위 체인

**[확정]** `hasPermissionsToUseToolInner`(`permissions.ts:1158`)가 고정 순서로 판정:
1. **deny 룰**(`:1170`, `getDenyRuleForTool`) → 즉시 `deny`
2. **ask 룰**(`:1184`, `getAskRuleForTool`) → `ask` (Bash 샌드박스 예외 있음)
3. **tool.checkPermissions**(`:1259`) — 도구 자체 판정
4. **bypass 모드**(`:1268-1281`, `bypassPermissions` 또는 plan+bypass가용) → `allow`
5. **alwaysAllow 룰**(`:1284-1296`, `toolAlwaysAllowedRule`) → `allow`

한 번 허용한 것 재질문 안 함: 사용자가 "Always allow" 시 `persistPermissionUpdates`(`:426`)로 `alwaysAllowRules`에 저장 → 이후 5단계에서 자동 allow. 모드별 자동화: `dontAsk` 모드는 `ask`를 `deny`로 변환(`:505-516`), `auto` 모드는 사용자 프롬프트 대신 **AI 분류기(side_query)**로 자동 판정(`:518-524`), auto 모드에서 allow 시 연속거부 카운터 리셋(`:486-499`). 헤드리스 에이전트는 PermissionRequest 훅 후 auto-deny(`:400-471`).

## 7) 기타 지능적 게이트

**[확정][하드] isConcurrencySafe 도구별 상이**: 읽기전용은 상수 true(`FileReadTool.ts:373`, `GlobTool.ts:76`, `GrepTool.ts:183`, Web 계열). 쓰기 도구는 기본 false. **Bash는 동적** — `isConcurrencySafe(input){ return this.isReadOnly?.(input) ?? false }`(`BashTool.tsx:434`), 즉 명령을 파싱해 읽기전용 명령(`ls`, `cat` 등)만 병렬 배치 허용. MCP 인증툴은 명시적 false(`McpAuthTool.ts:67`). 이 판정이 3번 스마트 배치의 입력이 됩니다.

**[확정][하드] Plan 모드**: `mode==='plan'`은 코드로 강제되는 권한 모드로, 편집/쓰기 도구의 `checkPermissions`가 비-allow를 반환해 차단합니다(모드 필드가 `permissions.ts:523,1270`, `filesystem.ts:1446` 등에서 검사됨; bypass 가용 시 예외 `:1270`). `EnterPlanModeTool`/`ExitPlanModeV2Tool`로 진입/이탈하며, 에이전트 컨텍스트에서는 진입 자체를 throw로 금지(`EnterPlanModeTool.ts:79`).

**[확정][소프트] TodoWrite**: 강제 없음. 프롬프트로만 유도 — "proactively 사용"(`TodoWriteTool/prompt.ts:7`), 단 "사소한 단일 작업엔 쓰지 말라"(`:25`). 코드가 TodoWrite를 강요하는 게이트는 없습니다.

**[확정][하드] PreToolUse 훅 입력 수정**: 훅이 `hookUpdatedInput`을 반환하면 `processedInput`을 교체해 이후 권한/실행에 반영(`toolExecution.ts:834-838`). 훅이 `deny`/`stop`으로 실행을 막을 수도 있음(`:848-860`).

- `true` → exec만 쓰는 code-mode 전용 모드

## 핵심: Code Mode도 결국 function calling 위에 있다

Code Mode 안에서 `await tools.exec_command(...)`를 호출하면, 그게 **내부적으로 실제 도구 디스패치(function 실행)로 연결**됩니다. 즉 Code Mode는 function calling을 **없앤 게 아니라**, 모델과 도구 사이에 **JS 오케스트레이션 레이어를 한 겹 끼운 것**입니다.

```
[기본]      모델 → function_call: shell(...) → 실행 → 결과가 컨텍스트로
[Code Mode] 모델 → exec(JS) → tools.shell(...) 여러 번 → 필요한 것만 text()로 방출
                              └ 이 tools.* 도 결국 같은 도구 디스패치
```

정리하면:
- **Codex = function-calling 에이전트** (맞음, 기본)
- **Code Mode = 토큰 절약용 옵션 레이어** (function calling을 코드로 감쌈)
- Claude Code도 똑같습니다 — 기본은 `tool_use`(function calling), PTC는 선택 기능

두 에이전트 다 **뿌리는 function calling**이고, "코드로 도구를 묶는" 모드는 양쪽 다 그 위에 얹은 최적화입니다.

## Claude Code — 정적 파티션 (배치를 미리 만듦)

`partitionToolCalls`가 **순서 보존 + 연속된 초록끼리만 병합** 규칙으로 나눔:

```
Read   → 배치1 [Read]           (초록, 새 배치)
Edit   → 배치2 [Edit]           (빨강 → 끊김)
Read   → 배치3 [Read]           (직전이 빨강이라 못 붙음 → 새 배치)
Read   → 배치3 [Read, Read]     (직전이 초록 → 병합!)
Write  → 배치4 [Write]          (빨강 → 끊김)
```
실행:
```
배치1 [Read]        ─▶ ⛔barrier
배치2 [Edit]        ─▶ ⛔barrier
배치3 [Read ‖ Read] ─▶ ⛔barrier   ← 이 둘만 동시
배치4 [Write]       ─▶ 끝
```
**4개 배치.** 첫 Read와 뒤의 Read 2개는 **사이에 Edit이 껴서 못 묶임**(파편화). 배치3의 Read 2개만 병렬.

## Codex — 동적 락 (배치 없음, 각자 spawn)

5개를 전부 `tokio::spawn`하고 순서대로 RwLock 락 요청 (write 우선 + FuturesOrdered로 순서 보존):

| | Codex | Claude Code |
|---|---|---|

## 1. "절단하면 캐시 깨지지 않냐?" → 안 깨져요. 오히려 그게 지키는 방법

포인트는 **자르는 타이밍**입니다.

```
도구 결과가 히스토리 [끝]에 새로 append 될 때 ─ 그 순간 자름 (append + truncate 동시)
                                                    │
   이미 캐시된 앞부분(prefix)은 안 건드림 ──────────┘  → 캐시 유지 ✓
   잘린 결과는 그대로 굳어서 다음 턴부터 prefix의 일부가 됨 → 그것도 캐시됨 ✓
```

캐시가 깨지는 건 **"이미 히스토리에 있던 과거 항목을 나중에 다시 자를 때"**입니다. Codex는 그걸 안 해요 — **넣을 때 딱 한 번** 자르고 끝. 그래서 append-only가 유지됩니다.

오히려 위험한 건 CC의 `applyToolResultBudget`처럼 **매 사이클 과거 결과를 재절단**하는 방식인데(그때 중간이 바뀜), CC는 그래서 `cache_control` breakpoint로 명시 관리하는 거고요. 즉 **Codex의 "기록 시점 1회 절단" = 캐시를 안 깨려는 설계**입니다. 걱정 안 하셔도 돼요 👍

## 2. Codex만의 것 — CC 프레임에 아예 없는 축들

맞아요, 지금까지 CC 인터페이스(루프·배치·압축·캐싱)에 맞춰 대조했는데, Codex는 **CC에 대응 개념이 없는 독자 설계**가 꽤 있습니다:

| Codex 고유 | 무엇 | CC엔? |
|---|---|---|
| **Responses API (stateful)** | 서버가 reasoning·상태를 `previous_response_id`로 이어감. reasoning을 `encrypted_content`로 보관 → 서버가 추론을 재사용 | Messages API는 **stateless**. 매번 전체 재전송 |
| **커널 샌드박스 스택** | Seatbelt/Landlock/bwrap **+ execpolicy(Starlark DSL) + network-proxy(egress MITM)** | 권한 정책·훅만. **OS/네트워크 격리 없음** |
| **exec-server** | 도구를 **원격·다른 OS**에서 실행 (릴레이 프로토콜) — 로컬 Mac에서 원격 Windows 셸 실행 | 없음 (worktree/remote isolation은 성격 다름) |
| **rollout(JSONL) + resume/fork** | 모든 항목을 스트리밍 즉시 기록 → 세션을 **임의 지점에서 재개·분기** + SQLite 미러 | 트랜스크립트 기록·resume는 있으나 fork/재구성은 다름 |

### 이 중 진짜 "Codex를 Codex답게" 만드는 3가지

1. **Responses API의 stateful 패러다임** — 이게 가장 근본적입니다. CC는 매 턴 대화 전체를 stateless로 재전송하지만, Codex는 **서버가 reasoning/상태를 이어가는** 구조예요. 앞서 본 `prompt_cache_key`, `encrypted_content` reasoning, WebSocket 세션 캐싱이 전부 이 패러다임의 산물입니다. CC의 "cache_control 직접 심기"가 필요 없는 이유이기도 하고요.

2. **실행 안전을 "커널 + 정책 + 네트워크"로 3중 격리** — CC는 "이 도구 써도 돼?"를 권한 정책으로 묻지만, Codex는 아예 **OS 커널 샌드박스 안에서** 돌리고, 명령은 **Starlark 프로그램(execpolicy)**으로 판정하고, 네트워크는 **MITM 프록시**로 거릅니다. "위험하면 물어본다"가 아니라 "위험해도 못 빠져나가게 가둔다".

3. **exec-server로 실행 위치를 분리** — 도구 실행을 **로컬이 아닌 원격·이종 OS**로 보낼 수 있어요. 에이전트는 Mac에서 돌지만 실제 `npm test`는 원격 Linux 컨테이너에서 도는 식. 이건 CC엔 없는 축입니다.
