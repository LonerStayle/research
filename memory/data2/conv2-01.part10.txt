## "설명문(description)"의 정체 — 소스 파일이 아니라 **매 요청의 메뉴판**

```
[개발자가 쓰는 곳]                        [모델이 읽는 곳]
tools/GlobTool/prompt.ts                  매 API 요청의 tools 배열
  export const DESCRIPTION =                {
    "- Fast file pattern matching..."  ──▶    "name": "Glob",
                                              "description": "- Fast file pattern...",
                                              "input_schema": { pattern, path }
                                            },
tools/GrepTool/prompt.ts             ──▶    { "name": "Grep", "description": "...NEVER
                                              invoke grep as Bash...", ... },
tools/FileReadTool/prompt.ts         ──▶    { "name": "Read", "description": "...must be
                                              an absolute path...", ... }
          ↑                                        ↑
   소스코드 속 문자열                    toolToAPISchema가 조립 (claude.ts:1235)
                                        → system·messages와 함께 매 요청마다 전송
```

즉 `tools/GlobTool/prompt.ts` 같은 파일은 **개발자용 보관 장소**일 뿐이고, 그 문자열이 **매 API 요청의 `tools` 배열에 실려서** 모델에게 갑니다. 모델 입장에선 시스템프롬프트 옆에 항상 붙어 오는 **"도구 메뉴판"** — 식당 메뉴판에 "이 메뉴는 2인분부터" 같은 안내가 적혀 있는 것과 같아요. 지난번 올드스쿨 툴콜링 정리에서 "프롬프트 적는 곳 3곳" 중 **②번(tool description)**이 바로 이겁니다.

## 그럼 "깔때기가 전부 설명서에 들어있냐" — **아니요, 사는 곳이 세 군데로 갈립니다**

| 깔때기 요소 | 어디에 사나 | 모델이 어떻게 아나 |
|---|---|---|
| **니치 선언** ("이름 찾을 땐 나") | description 문자열 | 메뉴판에서 **읽어서** 앎 |
| **입력 계약** ("절대경로 내놔") | description + **input_schema**(파라미터 정의) | 메뉴판에서 **읽어서** 앎 |
| **출력 부피 상한** (100개 잘림, 2000줄) | **도구 구현 코드** (설명서 아님) | 실행해보고 결과로 **겪어서** 앎 |
| **출력→입력 연결** (Glob 결과를 Grep에) | **어디에도 안 적혀 있음** | 모델이 tool_result 보고 **스스로 추론** |

마지막 줄이 핵심이에요. "Glob 다음에 Grep 해라"라는 문장은 **소스 어디에도 없습니다.** 있는 건:

1. Glob 메뉴 설명: "이름 패턴으로 파일 찾는 도구" → 실행하면 **경로 목록**이 tool_result로 돌아옴
2. Grep 메뉴 설명: "내용 검색, glob 파라미터로 파일 좁힐 수 있음"
3. 모델이 1의 결과(경로들)를 보고 "아, 이걸 2의 glob 파라미터에 넣으면 되겠네" — **이 연결은 모델의 추론**

그래서 "깔때기 설계"라는 표현의 정확한 의미는 — 순서를 적어놓은 게 아니라, **각 도구의 메뉴 설명(니치·입력조건)과 반환물 모양을 잘 깎아놔서, 합리적인 모델이라면 그 순서로 이을 수밖에 없게 만든 것**입니다. 레고 블록의 요철을 맞물리게 깎아놓은 거지, 조립 설명서를 쓴 게 아니에요.

그리고 방금 대표님이 잡아낸 정정도 이 표에 반영했습니다 — "비용 경사"는 코드에 없고(비용 계산 코드 0건), 실재하는 건 **출력량 상한**(Glob 100개 잘림 / Grep head_limit / Read 2000줄+토큰상한)이라 md·html 둘 다 "출력 부피 경사 + 해석 표기"로 고쳤어요.

- 진짜 배선된 의존은 **Read 하나뿐** (file_path 필수 → 경로는 검색 결과에서만 나옴)

```

## 맞는 부분 (핵심을 정확히 잡으심)

**"순서에 관한 상호 언급은 0건"** — 이게 정확합니다. 어떤 설명서에도 "나를 쓰기 전에 Glob을 써라", "Glob의 출력을 나한테 넣어라"가 없어요. 각 도구는:

- 자기 **니치**만 선언 ("이름 패턴으로 찾을 때 나")
- 자기 **필수 입력**만 선언 ("절대경로 내놔")

그리고 "Read가 요구하는 경로를 어디서 구하지? → 아, 검색 결과에서" — **이 연결은 순전히 LLM의 추론**입니다. 대표님 문장 그대로예요.

## 다듬을 부분 하나 — "다른 도구를 언급하지 않고"는 절반만 사실

설명서에 다른 도구 언급이 **있긴 있어요**. 다만 용도가 다릅니다:

| 언급 종류 | 존재 여부 | 예시 |
|---|---|---|
| **순서 지시** ("누구 다음에 나") | ❌ 0건 | — |
| **탈출구** ("이 경우엔 딴 데로") | ✅ 있음 | "열린 탐색이면 **Agent** 써라" |
| **우회 금지** ("나 대신 딴 걸로 하지 마") | ✅ 있음 | "**절대** grep을 Bash로 호출 마라" |

즉 "서로를 몰라서" 순서가 나오는 게 아니라 — **"서로의 순서를 말하지 않아서"** 순서가 LLM 추론으로 나오는 거예요.
