## 세팅 방법 (사용자 쪽)

`.claude/rules/*.md` 파일에 YAML frontmatter로 적용 경로를 선언합니다:

```markdown
---
paths: src/api/**
---
API 코드 작업 시 지켜야 할 규칙...
```

이 `paths` 유무가 rule의 운명을 가릅니다 (`src/utils/claudemd.ts:254-279`, `:773`):

| frontmatter | 분류 | 로딩 시점 |
|---|---|---|
| `paths` 없음 (또는 `**` 전체 매칭) | **무조건부 rule** | 세션 시작 시 CLAUDE.md와 함께 병합 → 0번 메시지에 포함 |
| `paths: <글롭>` 있음 | **조건부 rule** | 시작 시엔 안 실림 — **매칭되는 파일을 건드릴 때** 지연 주입 |

스코프는 3곳에서 스캔합니다: Managed, User(`~/.claude/rules/`), Project(각 디렉토리의 `.claude/rules/`) — 하위 디렉토리 재귀 포함 (`claudemd.ts:697-778`).

## 런타임 동작 (지연 주입 파이프라인)

1. **트리거 등록**: Read 도구가 파일을 읽으면 그 경로를 `context.nestedMemoryAttachmentTriggers` Set에 넣습니다 (`FileReadTool.ts:848,870,1038` — Set 자체는 `QueryEngine.ts:370,518`에서 생성).

2. **수집**: 다음 ReAct 사이클의 어태치먼트 수집 때 `getNestedMemoryAttachments`가 트리거 Set을 순회하고 비웁니다 (`attachments.ts:872, 2182, 2191`). 도구 실행 → 트리거 적재 → 다음 전처리에서 수거, 순서가 보장되도록 배치돼 있습니다 (`attachments.ts:818` 주석).

3. **매칭**: 트리거된 경로마다 두 갈래로 rule을 찾습니다 —
   - Managed/User 조건부 rule: `getManagedAndUserConditionalRules(targetPath, ...)` (`claudemd.ts:1205`)
   - CWD→대상 파일 사이의 중첩 디렉토리들: 각 디렉토리의 `CLAUDE.md` + `.claude/rules/` (`getMemoryFilesForNestedDirectory`, `claudemd.ts:1249`)
   
   글롭 매칭은 `ignore` 라이브러리, 즉 **gitignore 문법**으로 상대경로를 판정합니다 (`claudemd.ts:1369-1395`).

4. **주입**: 매칭된 rule은 `nested_memory` 어태치먼트가 되어 `"Contents of <경로>:\n\n<내용>"` 형태의 system-reminder 유저 메시지로 삽입됩니다 (`messages.ts:3700-3707`) — skill_listing과 같은 어태치먼트 트랙이에요.

5. **중복 방지**: 한 번 주입된 rule은 `loadedNestedMemoryPaths`(축출 없는 Set)로 세션 내 재주입을 막습니다. `readFileState`만 쓰면 100개 LRU라 바쁜 세션에서 밀려나 같은 rule이 반복 주입되는 버그가 있어서 별도 Set을 둔 것까지 주석에 남아 있습니다 (`attachments.ts:1718-1732`).

정리하면: **선언은 정적(frontmatter 글롭), 발동은 동적(파일 접근 이벤트)**입니다. "필요한 상황"의 정의가 곧 "그 글롭에 매칭되는 파일을 도구가 실제로 건드린 순간"이고, 그래서 안 쓰는 영역의 rule은 컨텍스트를 한 바이트도 안 먹다가 해당 코드를 만지는 순간에만 끌려 들어옵니다.

## 요점 세 개

1. **세팅은 frontmatter의 `paths:` 한 줄이 전부**입니다. 그게 있으면 "조건부", 없으면 CLAUDE.md처럼 처음부터 로드.
2. **"필요한 상황"의 판정 기준 = 클로드가 도구로 그 패턴에 맞는 파일을 실제로 읽었는가**입니다. 유저 말의 의미를 AI가 분석해서 가져오는 게 아니라, 파일 접근이라는 기계적인 이벤트로 발동합니다.
3. 발동하면 rule 내용이 **대화 중간에 유저 메시지(system-reminder)로 끼어드는** 것뿐이에요. 특별한 채널이 있는 게 아닙니다.

이러면 rule을 100개 만들어놔도 평소엔 토큰을 하나도 안 먹고, 해당 영역을 건드리는 세션에서만 그 rule이 올라옵니다. 어떤 부분이 걸리셨던 건지 말씀해주시면 거기만 더 파볼게요.

## 1단계 — Read는 그냥 "쪽지만 남김"

Read 도구 코드 안에 직접 이 한 줄이 박혀 있습니다 (`FileReadTool.ts:848`):

```ts
context.nestedMemoryAttachmentTriggers?.add(fullFilePath)
```

이벤트 리스너나 훅 등록 같은 게 아니라, Read가 자기 일(파일 읽기) 하는 김에 **컨텍스트에 있는 Set에 경로를 하나 추가**하는 게 전부입니다. 이 시점엔 rule 매칭도, 주입도 일어나지 않아요. 그리고 Read는 이 Set 처리를 기다리지 않고 그냥 끝납니다.

## 2단계 — 다음 사이클 전처리가 우편함을 비움

앞에서 봤던 ReAct 사이클 전처리(매 모델 호출 직전에 어차피 도는 어태치먼트 수집 단계) 안에 `nested_memory` 수집기가 원래 들어 있습니다 (`attachments.ts:872`). 얘가 자기 차례가 오면:

```
Set을 순회 (:2182) → 각 경로마다 글롭 매칭 → 매칭된 rule을 어태치먼트로 생성 → Set 비움 (:2191)
```

## 그림으로

```
[사이클 N]   모델: "Read src/api/user.ts 호출"
             Read 실행 → 파일 내용 반환 + Set에 경로 add  ← 여기까지가 Read의 역할
                                          │
[사이클 N+1] 전처리(어태치먼트 수집) ──────┘
             Set 열어봄 → "src/api/user.ts 있네" → rule 글롭 매칭
             → nested_memory 어태치먼트 생성 → system-reminder 메시지로 삽입
             모델 호출 (이때부터 rule이 보임)
```

훅과의 차이를 짚으면:

- **즉시성 없음** — Read 시점에 발동하는 인터셉터가 아니라, 다음 전처리 때 **배치로** 처리됩니다. 그래서 한 배치에서 파일 10개를 병렬 Read해도 rule 매칭은 다음 전처리에서 한 번에 이뤄집니다.
- **등록 메커니즘 없음** — 콜백/이벤트 시스템이 아니라 그냥 공유 Set 하나(`QueryEngine.ts:370`에서 생성)를 쓰는 생산자-소비자 구조입니다. Read가 생산자, 전처리가 소비자.
- 참고로 CC의 진짜 훅 시스템(PreToolUse/PostToolUse)은 별도로 존재하는데, 이 rule 주입은 그 훅 시스템을 안 탑니다.

그래서 정확한 한 줄 요약은: **"Read가 잡아서 넣는" 게 아니라 "Read는 표시만 하고, 매 사이클 도는 전처리가 표시된 걸 보고 넣는"** 구조입니다.

| | 어태치먼트 수집 | 컨텍스트 전처리 (5단) |
|---|---|---|
