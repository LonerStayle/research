## ④⑤ 로드의 실체 — 여기가 제일 흥미롭습니다

검색 결과는 텍스트가 아니라 **`tool_reference` 블록**으로 tool_result에 박힙니다 (:462-469):

```ts
content: content.matches.map(name => ({ type: 'tool_reference', tool_name: name }))
```

그리고 요청 조립부(claude.ts:1154-1167)의 규칙:

```
비 deferred 도구        → 항상 전송
ToolSearch 자신         → 항상 전송
deferred + 미발견       → tools 배열에서 아예 제외!   ← 사전 선언 자체를 안 함
deferred + 발견됨       → 전송 (defer_loading: true 플래그, api.ts:223)
```

"발견됨" 판정은 별도 상태 저장소가 아니라 **대화 이력 자체를 스캔**해서 얻습니다 — `extractDiscoveredToolNames`(toolSearch.ts:545-592)가 이력의 tool_result 속 tool_reference 블록을 전부 긁어 집합을 재구성해요. 대화가 곧 영수증인 거죠. compact로 그 메시지가 날아가면? **compact_boundary 마커에 `preCompactDiscoveredTools`로 스냅숏을 이월**해서 발견 집합이 살아남습니다 (:553-558).

스키마의 실제 "확장"은 클라이언트가 아니라 **API 서버**가 합니다 — tool_reference를 모델 컨텍스트에서 full definition으로 펼치는 베타 기능이라, 베타 헤더가 필수 (1P/Foundry는 advanced-tool-use, Vertex/Bedrock은 tool-search-tool, claude.ts:1174-1182). Bedrock/Vertex는 미지원일 수 있다는 주석도 있고요 (ToolSearchTool.ts:441-443).

## 첫 발행이 1턴에 붙는 이유

`deferred_tools_delta`는 어태치먼트 파이프라인의 정식 멤버입니다 (`attachments.ts:836`). 델타 계산은 "현재 풀 − 이미 고지한 집합"인데, **세션 첫 턴엔 고지 이력이 0이니까 델타 = 전체 deferred 목록**이 됩니다. 그래서 세션의 첫 수집 지점 — 즉 첫 유저 프롬프트 처리 시점 — 에 최초 전체 목록이 발행돼요. (텔레메트리 주석도 이를 명시: "subagent getAttachments → prior=0 is EXPECTED — fresh conversation", toolSearch.ts:606-608. compact 직후 재발행도 같은 원리 — 옛 고지 메시지가 요약으로 날아가서 prior=0.)

## 1턴 messages 배열의 실제 배치

```
[0] 유령 메시지            ← claudeMd·userEmail·currentDate (별개 트랙, prependUserContext)
[1] 유저의 첫 프롬프트      ← 대표님이 타이핑한 텍스트 그대로
[2] deferred_tools_delta   ← ⟨system-reminder⟩ The following deferred tools are
                              now available via ToolSearch: ... (isMeta user 메시지)
[3] skill_listing          ← 스킬 카드 목록 (같은 파이프라인 이웃)
[4] agent_listing_delta / mcp_instructions_delta ...
```

즉 유저 프롬프트 텍스트에 섞이는 것도 아니고, 0번 유령 메시지에 합쳐지는 것도 아니고, **프롬프트 직후에 별도 isMeta 메시지로 나란히 서는 겁니다.** 방금 확인한 소스에서 이 델타 4형제가 같은 목록에 연달아 등록돼 있어요 — `deferred_tools_delta`(:836) · `agent_listing_delta`(:851) · `mcp_instructions_delta`(:854) · `skill_listing`(:875).

## 발행 전 통과해야 하는 문 4개 (attachments.ts:1461-1471)

첫 턴이라도 이 게이트를 못 넘으면 안 들어옵니다: ① 델타 모드 켜짐 ② tool search 활성 ③ 모델이 tool_reference 지원 (haiku 계열이면 탈락) ④ ToolSearch 도구가 disallowed 아님. 주석이 이유를 설명해요 — "어태치먼트 문구가 'available via ToolSearch'라고 말하니, ToolSearch가 실제로 요청에 있어야 한다."

## 모델이 까먹었을 때의 4중 안전망 (전부 소스 확인)

**① 입구 표지판은 안 묻힘** — ToolSearch 도구의 설명문("Deferred tools appear by name in system-reminder messages")은 대화 이력이 아니라 **tools 배열에 매 요청 fresh하게** 실립니다. "정확한 목록"은 묻혀도 "그런 목록이 존재하고 검색하면 된다"는 사실 자체는 항상 눈앞에 있어요.

**② 키워드 검색** — 이름을 정확히 기억 못 해도 `"notebook jupyter"`처럼 의미로 던지면 점수 검색이 찾아줍니다. 목록 암기가 전제 조건이 아니에요.

**③ bare-name fast path** — 결정적 증거가 이 주석입니다 (ToolSearchTool.ts:194-198):

> "Handles models using a bare tool name instead of select: prefix (**seen from subagents/post-compaction**)"

"compact 후·서브에이전트에서 모델이 흐릿한 기억으로 이름만 던지는 걸 관찰했다" — **기억 열화 상황을 실측하고 그걸 겨냥해 만든 방어선**이라는 뜻이죠.

**④ 실패해도 회복 유도** — 매치 0이면 "No matching deferred tools found" + 연결 중 서버 안내로 재시도를 유도합니다.

## 그리고 compact가 역설적으로 리프레시 장치

가장 재미있는 부분인데, 고지가 너무 오래돼서 묻힐 때쯤이면 보통 compact가 옵니다. 그런데 compact는 옛 고지 메시지들을 요약으로 날려버리죠 → 다음 델타 스캔에서 "고지한 적 없음(prior=0)"이 되고 → **전체 목록이 새 컨텍스트 맨 앞쪽에 통째로 재발행**됩니다. 소스 근거:

- `getDeferredToolsDeltaAttachment`가 compact.ts에서도 호출되도록 export됨 — "the gate must be identical at both call sites" (attachments.ts:1454-1455)
- 텔레메트리 주석: "**compact_full: compact.ts passes [] → prior=0 is EXPECTED**" (toolSearch.ts:608)

실측도 있습니다 — 이 세션 compact 직후 첫 리마인더에 deferred 전체 목록이 다시 들어왔었죠. 즉 lost-in-the-middle가 최악이 되는 시점(초장기 대화)에 컨텍스트가 리셋되면서 목록도 앞쪽으로 끌어올려지는 구조예요. 영수증(tool_reference) 쪽도 별도 보호 — snip은 영수증 보유 메시지를 제거 대상에서 제외하고(toolSearch.ts:539-540), compact는 발견 집합을 boundary 마커에 스냅숏으로 이월합니다.

## Q2. 키워드 검색이 BM25인가?

**아닙니다. BM25의 핵심 요소가 전부 빠진, 손으로 짠 가중 매칭입니다.** 소스(ToolSearchTool.ts:266-291) 기준 비교:

| BM25 구성 요소 | ToolSearch에 있나 |
|---|---|
| TF (단어 빈도 — 많이 나올수록 가점) | ✗ — `pattern.test()`는 불리언, 1번이든 10번이든 동일 점수 |
| IDF (희귀 단어 가중 — 흔한 단어 감점) | ✗ — 말뭉치 통계 자체가 없음 |
| 문서 길이 정규화 | ✗ — 설명 길이 무관 |
| 필드별 가중치 | ✓ 이것만 유사 — 이름 정확(12/10) > 이름 부분(6/5) > 힌트(4) > 설명(2) |

정확히 부르면 **"필드 가중치를 손으로 박은 불리언 매칭 + 합산 정렬"**입니다. BM25F에서 TF·IDF·정규화를 다 떼어낸 껍데기에 가깝죠. 랭킹 이론 없이 "이름에 맞으면 세게, 설명에 맞으면 약하게"라는 직관을 상수로 하드코딩한 거예요.

왜 이렇게 조악해도 되냐면 — 앞서 본 그 이유입니다. 검색 대상이 수백 건짜리 미니 목록이고(코퍼스 통계가 무의미한 규모), 쿼리 작성자가 LLM이라 실패하면 단어를 바꿔 재시도하니까, 정교한 랭킹의 투자 대비 효용이 낮은 겁니다. 검색 엔진이 아니라 **"LLM용 그물망"** 수준으로 설계 눈높이를 잡은 거죠.

    }
  }
  return false
}
