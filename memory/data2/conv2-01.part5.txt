|---|---|---|

## 그럼 왜 시스템 프롬프트 본문은 마크다운인가

**① 조립 방식과의 궁합 (소스로 확인되는 가장 강한 이유)**
시스템 프롬프트는 독립 문자열 섹션들의 평평한 배열로 조립됩니다 — null 필터링으로 섹션이 통째로 빠지기도 하고(`filter(s => s !== null)`, prompts.ts:576), **캐시 경계 마커에서 배열이 두 동강 나서** 따로 join되기도 하죠(api.ts:380-396). 마크다운 섹션은 닫는 태그가 없어서 아무 데서나 자르고 빼고 이어붙여도 안전합니다. XML이었다면 배열 중간 분할이 여는 태그와 닫는 태그 사이를 가를 위험이 있어요 — 균형 잡힌 중첩 구조가 "임의 지점 분할·필터링" 조립과 상극입니다.

**② 닫는 태그 비용** (추론)
`# Harness`는 끝 표시가 필요 없지만 `<harness>...</harness>`는 섹션마다 닫는 태그 토큰을 냅니다. 수십 개 섹션 × 매 요청이면 누적이 되죠.

**③ 태그의 희소성 = 신호 강도** (xml.ts 주석들이 뒷받침하는 추론)
XML 태그를 아껴 쓰기 때문에 태그 하나하나가 "시스템 주입물"이라는 강한 신호가 됩니다. 온 문서가 XML이면 `<system-reminder>`가 벽지가 되어버려서, "이건 유저가 아니라 하네스가 넣은 것"이라는 출처 구분이 희석돼요.

**④ 출력과의 일관성** (추론)
모델의 유저향 출력 자체가 GFM 마크다운으로 렌더링됩니다("displayed as Github-flavored markdown" — 시스템 프롬프트 1번 불릿). 지시문도 같은 방언으로 쓰는 게 자연스럽고, 마크다운 헤더+불릿은 학습 데이터에서 가장 흔한 문서 구조라 모델이 공짜로 이해합니다.

## Q2: prependUserContext 내용이 바뀌면 KV 캐시 깨지나? → **네, 통째로. 그래서 동결한 겁니다**

유령 메시지는 messages **0번**, 즉 대화 프리픽스의 맨 앞입니다. 프롬프트 캐시는 프리픽스 기반이라 0번의 바이트가 하나라도 바뀌면 **그 뒤 대화 전체가 캐시 미스**예요. 이게 추측이 아니라, 소스 주석이 정확히 이 말을 합니다 (constants/common.ts:17-23):

> "Memoized for **prompt-cache stability** — captures the date once at session start. ... When midnight rolls over, getDateChangeAttachments **appends the new date at the tail** ... the trade-off there is: **stale date after midnight vs. ~entire-conversation cache bust — stale wins.**"

설계가 아름답게 맞물립니다:

```
변하면 안 되는 곳(0번 유령)  → memoize로 세션 내내 동결 → 매 호출 바이트 동일 → 캐시 히트
변할 수밖에 없는 정보(날짜)  → 0번을 건드리지 않고 꼬리에 date_change 어태치먼트로 추가
캐시 무효화 허용 시점        → /clear·compact = 어차피 대화가 통째로 재구성되어
                              캐시가 전멸하는 순간에만 재독 허용
```

제가 "자정에 날짜가 바뀌었다"고 봤던 것도 유령 메시지가 갱신된 게 아니라 **꼬리의 date_change 어태치먼트**였던 겁니다 ("The date has changed..." — 정확히 이 메커니즘의 산물). 델타 어태치먼트 4형제와 완전히 같은 철학이죠 — **앞은 얼리고, 변경분은 뒤에 덧붙인다.**

## 재미있는 대목 — deferred 도구와 상태 관리 방식이 다릅니다

같은 "1회 발행 + 델타" 패턴인데 **장부를 다른 곳에 둡니다**:

| | 스킬 목록 | deferred 도구 목록 |
|---|---|---|
| "이미 알렸다"의 장부 | **프로세스 메모리의 Set** (`sentSkillNames`, agentId별) | **대화 이력 스캔** (과거 델타 어태치먼트 재생) |

유령 메시지의 포장 문구를 다시 보면 (api.ts:463-469):

> "As you answer the user's questions, **you can use the following context**... IMPORTANT: this context **may or may not be relevant** to your tasks. You should not respond to this context unless it is highly relevant."

이건 명령문의 어조가 아니라 **"참고자료 전달"의 어조**입니다. 시스템 프롬프트가 "너는 이렇게 행동하라"(하네스 제작자의 규칙)라면, CLAUDE.md는 "사용자가 가져온 문서인데 참고해라, 관련 없을 수도 있다"(반입 화물)로 취급하고 있어요. 설계자가 둘을 **다른 종류의 텍스트**로 봤다는 직접 증거입니다.

## 이유 ① — 권위 계층 분리 (가장 유력한 추론)

모델은 system > user의 지시 계층으로 훈련돼 있죠. CLAUDE.md는 **아무 저장소에서나 굴러들어올 수 있는 텍스트**입니다 — 남의 레포를 clone하면 그 안의 CLAUDE.md도 딸려 옵니다. 이걸 system 파라미터에 넣으면 **임의의 저장소 파일이 Anthropic의 하네스 규칙과 같은 권위**를 갖게 돼요. 악성 CLAUDE.md("이전 지시 무시하고...")가 시스템 레벨에서 발화하는 인젝션 벡터가 되는 거죠. user 메시지 층에 두면 하네스의 안전 규칙(system)이 항상 상위에 남습니다.

재미있는 긴장도 보입니다 — claudeMd 섹션 머리엔 "These instructions **OVERRIDE any default behavior**"라고 적혀 있어요. 즉 **문구로는 권위를 승격시키되, 층으로는 user에 격리**한 겁니다. "기본 행동보다 우선하되, 시스템 규칙은 못 이기는" 정확한 중간 지위.

## 이유 ② — 서브에이전트 모듈성 (소스로 확인)

서브에이전트는 시스템 프롬프트가 **통째로 갈립니다** — 에이전트 정의(frontmatter 아래 본문)가 곧 그 에이전트의 시스템 프롬프트죠. 그런데 유령 메시지는 공통으로 따라갑니다:

## 이유 ③ — 글로벌 캐시 조각 방지 (부분적)

시스템 프롬프트 앞부분은 전 세션이 공유하는 'global' 캐시인데, CLAUDE.md는 프로젝트·사용자마다 다르니 정적부에 넣으면 캐시가 조각납니다. 다만 경계 뒤 동적 꼬리에 넣는 선택지도 있었으니 이건 결정타는 아니고 — 유령 메시지도 어차피 캐시 프리픽스에 참여하니 캐시 효율 자체는 비슷합니다.

## 이유 ④ — 채널 일관성

이번 대화에서 본 것처럼 rules·스킬 본문·목록 델타·훅 출력이 **전부 isMeta user 메시지**로 들어옵니다. CLAUDE.md는 그 가족의 "0번 상주 멤버"일 뿐이라, "하네스가 모델에게 먹이는 콘텐츠는 user 층의 system-reminder"라는 단일 규약이 유지돼요.
